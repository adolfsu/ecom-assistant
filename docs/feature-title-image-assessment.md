# 新功能评估：同一商品批量复制相似品（逐条换标题 / 换主图 / 发布）

> 评估日期：2026-11-26　基于版本：2.0.2（`156d55a`）
> 场景更正：**不是**每次搜一个新 ID。而是**锁定一个源商品**，对它的列表行连点 N 次「发布相似品」，
> 每次打开一个新的发布页，填入各自的标题、换掉第一张主图，然后发布。

---

## 一、更正后的实际流程

```
前置（只做一次）
  在「商品列表」搜索源商品 ID → 确认「共 1 件」且精确命中 → 锁定这一行

循环 N 次（N = 你要做多少个变体）
  ┌ 定位源商品行（不重新搜索）
  ├ 点「发布相似品」→ 确认 → 新标签页打开发布页
  ├ 等发布页加载完（按钮可用 + 关键区块渲染）
  ├ 填这条的标题
  ├ 从图片空间选这条的主图，替换第一张
  └ 点「发布商品」→ 等提交成功/失败 → 关页，回到列表页
```

和现在的「批量发布相似品」相比，**差别只有两处**：
1. 搜索从「每条一次」变成「一次」；
2. 发布前多两个动作：填标题、换主图。

其余全部复用：确认弹窗、`window.open` 钩子、扩展代开兜底、标签页接管、发布结果判定、失败原因采集、任务记录、复制文本。

| # | 步骤 | 现状 | 可行性 | 风险 |
|---|---|---|---|---|
| 1 | 搜索源商品（一次） | 已实现，且现在能处理「列表只有 1 条」的情况 | **已完成** | 低 |
| 2 | 定位源商品行 → 点「发布相似品」→ 确认 | 已实现（`searchAndOpenSimilar` 第 831 行之后与搜索完全解耦，只依赖搜到的那一行） | **已完成** | 低 |
| 3 | 等发布页加载完 | 已实现（`publishNow` 开头） | **已完成** | 低 |

| 5 | 图片空间选主图，替换第一张 | **无任何现有能力** | **待验证** | **高** |

**好消息**：既然不用反复搜索，最大的历史故障源（搜索判定、串位）在这个功能里只出现一次，稳定性会比现在的批量发布更好；单条耗时也能省掉 5~20 秒的搜索校验。

## 三、第 5 步（换主图）为什么仍是唯一的高风险

难点不在「点按钮」，而在我看不到真实页面。以下五点决定它是「一天能做完」还是「做不了」：

### 1. 图片空间是 iframe 还是同层弹层
同源 iframe 可操作；跨域 iframe 需要 `executeScript({ allFrames })` 并按 frameId 派发；同层弹层最好办。**未知**。

### 2. 图片怎么被认出来（决定输入表怎么写）
要按「这条用哪张图」批量匹配，程序必须能读到图片的标识，可能是：
- 卡片上的素材名 / 文件名文本
- `title` 或 `aria-label`
- hover 才出现的 tooltip
- 图片 URL 里的素材 ID

**如果页面只显示缩略图、名字必须逐张 hover 才出现**，那就只能边 hover 边匹配，慢而且容易错——这种情况我建议改需求（见第六节）。

### 3. 列表是否分页或虚拟滚动
几百上千张图时，找特定图要翻页/滚动，单条耗时会明显上升。

### 4. 「替换第一张」的交互语义（最关键）

| 页面提供的能力 | 难度 |
|---|---|
| hover 出现「设为主图」/右键菜单 | 简单 |
| 选中后「上移」按钮 | 可做；**HTML5 拖拽排序在合成事件下基本不可行** |
| 只能「删掉第一张 → 上传新图」（新图追加末尾） | **危险**，见下 |

第三种情况我倾向**不做**：删图是破坏性操作，万一中途失败，留下的是「主图残缺的草稿」，比不改更糟。而且如果你要连做几十个变体，一次失败就污染一个草稿。

### 5. 能否程序化提供本地图片文件
内容脚本无法给 `<input type=file>` 赋值。唯一正路是 `chrome.debugger` + `DOM.setFileInputFiles`，需要 `debugger` 权限，浏览器会常驻「正在调试此浏览器」提示条。默认不走这条路，坚持走图片空间选图。

## 四、这个场景**新引入**的三个风险

这是「连点同一行」才会出现的问题，和现在的批量发布不一样：

### 1. 串行闸门必须极严
N 次点击发生在同一行、同一个「发布相似品」入口上。如果上一条的发布页还没提交完就点了下一次，会出现**两个发布页同时存在**，抢同一份 storage、同一条任务记录，结果互相覆盖。
- 现有架构本来就是串行的（等 `SIMILAR_PUBLISH_DONE` 才进行下一条），这条路能走；
- 但需要新增一道硬保护：**必须确认上一条的发布页已关闭/已回报，才允许点下一次**；并且每次点击前重新确认「列表页仍是那一行」（点确认后列表可能刷新，旧的 DOM 引用会失效）。

### 2. 失败标签页堆积
现有行为是「发布失败就保留标签页，方便看校验提示」。做 30 个变体如果有 10 个失败，就会堆出 10 个标签页。
- 建议：失败页保留，但设上限（如只留最近 3 个，更早的自动关闭并把失败原因存进结果），否则跑完整个浏览器没法用。

### 3. 同一商品高频连发的平台侧反应（业务风险，非技术）
用户实测过「发过的商品可以再发」，但那是零星几次。**同一商品在一次任务里连发 10~50 次**是否触发限流/风控，没有验证过。
- 建议：批次间加固定间隔（如 5~8 秒），并提供「每次最多 N 条」的分段执行；先小批量（3~5 条）试跑，确认没问题再放开。

## 五、架构改动量（中等，不动核心链路）

| 改动点 | 说明 |
|---|---|
| 数据模型 | 从 `ids: string[]` 变成 `{ sourceId, variants: [{ title, image }] }` |
| 队列循环 | 循环体不再「搜索 + 点发布」，改为「定位行 + 点发布」，搜索只在开头做一次 |
| 搜索幂等 | 每轮开始前判断列表是否仍是「共 1 件 + 命中原 ID」：是则跳过搜索，**被重置则自动重搜一次**（不能硬跳过） |
| 发布页参数 | `SIMILAR_PUBLISH` 目前不带参数，需要新增「准备内容」通道承载标题与图片名（消息带 payload，或从 storage 读当前任务快照） |
| 功能登记 | `platforms/douyin/features/` 加一个文件 + `platforms/index.js` 加一行 import —— 顺便验证 2.0 注册中心确实做到「加功能不改导航」 |
| 结果结构 | 每条变体记录：标题、实际选中的图片名、失败原因；复制文本按「第几号变体」编号 |
| 失败页管理 | 保留上限 + 自动清理 |

不需要动：搜索判定、弹窗点击、标签页接管、发布结果判定、任务记录、复制格式。

## 六、半自动方案（用户已确认可接受）

如果图片空间无法稳定自动操作，就退到「人换图、机器跑流程」：

```
写完全部变体的标题后开始
  ↓
第 1 条：自动点复制 → 打开编辑页 → 自动填标题
  ↓ 发布页中央浮出提示
  ┌─────────────────────────────────┐
  │  第 1/10 条                       │
  │  主图请替换为：收纳袋B_白底_01.png   │
  │  [ 已完成换图，继续 ]  [ 停止整批 ]  │
  └─────────────────────────────────┘
  ↓ 用户手动从素材库选图、换好第一张，点「继续」
  ↓ 程序点「发布商品」→ 判结果 → 关页 → 下一条
  ↓
第 2 条 …（重复 N 次）
```

要点：

- **提示里必须写清这一条该用哪张图**（直接用表格里那一列的原值），否则几十条下来会记混；
- 浮层固定显示「第几条 / 共几条」和当前标题，避免串行；
- 「继续」才放行发布，不点就一直等（不超时跳条，避免把没换图的商品发出去）；
- 「停止整批」随时可退，已发布的不受影响；
- 这套机制只依赖「暂停 / 放行」闸门，**完全不碰图片空间**，所以几乎不可能因为页面改版而失效。

好处：图片由人眼确认，绝不会选错图；坏处：每条要手动点两下（换图 + 继续）。做 20 条大概多花 5~10 分钟。
如果探测发现图片空间可控，则在此之上再加「自动选图」，变成全自动；半自动保留为开关。

## 八、建议的交付顺序

**批次一（风险低，先交付）**：1 → 2 → 3 → 4 → 6
即「搜一次源商品 → 连点 N 次复制 → 每条填不同标题 → 发布」，主图步骤做成开关但默认关闭。
这一批已经能覆盖你「同款多链接、标题差异化」的需求，且稳定性高于现在的批量发布。

**批次二（先探测再实现）**：第 5 步换主图

## 九、探测工具（已内置到侧边栏）

**不再需要开 DevTools**：侧边栏 → 设置 → 「页面结构探测」→ 点「探测当前页面」。

用法：
1. 打开「发布相似品」后的商品编辑页；
2. 点主图区的「上传 / 选择图片」，**等图片列表显示出来**（弹窗不要关）；
3. 切回侧边栏 → 设置 → 点「探测当前页面」；
4. 结果出现在下方文本框，点「复制结果」发回。

实现：`app/shared/probe.js` 的 `probeFrame()` 以 `executeScript({ func, allFrames: true })` 注入，
所以**跨域 iframe 也能读**（Console 版读不到，这是它被取代的原因）。
报告内容：
- 哪些 frame 有响应、各自 URL、本层 iframe 的 src 与是否可访问；
- 图片密集容器的选择器、卡片 class、卡片文本；
- 前 3 张图的 `alt / title / data-* / aria-*`，以及卡内有没有名字元素；
- 是否有搜索框（能按素材名搜就绕开翻页）、有无勾选控件、有无分页/虚拟滚动；
- 「设为主图 / 上移 / 删除 / 确定」这类入口文案是否存在。

判定标准：
- 有搜索框 + 名字可读 → **全自动可行**；
- 名字不可读、或只能拖拽排序 → **走半自动**（第六节）；
- 素材库来自未授权域名（报告里 frame 无响应）→ 需要把该域名加进 `host_permissions`。

## 十、实测结论（2026-11-26，探测结果）

用户在商品编辑页打开素材库后跑了两次探测，第二次（探测逻辑改为「先找浮层、再找网格」之后）拿到了完整结构：

| 要素 | 实测结果 | 结论 |
|---|---|---|
| 形态 | 同层 DOM 弹层 `.ecom-g-modal-wrap`，`position:fixed`、z-index 1000 | 不需要跨 iframe，直接 DOM 操作 |
| 搜索框 | `placeholder="查询图片名称"`，class `ecom-g-input` | 可以按文件名搜，不用翻页找图 |
| 网格 | `div[class*="grid"]` → 卡片 `div.index-module_fileCard__JqjtD` | 选择器稳定（实现里仍用 `[class*="grid"]` + 卡内 `[class*="fileName"]`，不写死 hash） |
| 文件名 | `[class*="fileName"]` → 如 `800*8001.jpg` | **能精确校验选中的是哪张图** |
| 选中 | 每卡一个 checkbox | 点卡片后再校验 checkbox |
| 确认 | 底部「确定 / 取消」 | 有明确终点 |

主图的替换入口也确认了：**hover 主图第一张**会出现四个入口（智能创作 / 好图复刻 / 本地替换 / 图库替换），
点「图库替换」→ 素材库弹窗 → 搜名字 → 选第一个 → 确定，平台自己替换第一张。

用户补充的两条使用约定直接写进了实现与交互：
1. **搜索范围是当前文件夹**，用户会提前在素材库左侧选好目标文件夹；单文件夹内不会重名，所以「搜到的第一个结果」就是目标；
2. 图片名由**用户指定的本地文件夹**提供，与标题**顺序一一对应**，数量少的为准（23 标题 + 16 图 → 只跑 16 条）。

## 十一、最终实现（v2.1.0）

功能名 **批量复制变体**（`douyin.copy-variants`，分类「发布」，`component: copy-variants`）。

流程：

```
商品列表页：搜索源商品（整批仅一次）
  ↓ 循环 N 次（N = min(标题数, 图片数)）
  重新确认那一行仍在页面上（失效则补搜一次）
  → 写 variantPending{index, title, image}
  → 点「发布相似品」→ 确认 → 等新标签页被接管
      ↓ 发布页（similar.js 注入）
      填标题（校验写入值与 maxlength）
      → hover 主图第一张 → 点「图库替换」
      → 素材库搜文件名 → 校验首格名字 → 选中 → 确定
      → 校验主图第一张的 src 变了
      → 点「发布商品」→ 等「商品提交成功」
  → 回传结果 → 下一条
```

关键约束与取舍：

- **只搜一次**：`similar.js` 把原来的 `searchAndOpenSimilar` 拆成 `searchSource` 与 `openSimilarOnRow`，
  变体队列拿第一次的定位结果反复使用；`previousIds` 在每条开始前清空（变体是同一个 ID，否则会被「排除上一条」逻辑排掉）。
- **变体标记走消息，不走 storage 猜测**：列表页在 `SIMILAR_OPENED` 里带 `variant: true`，后台存进 pending 再随
  `SIMILAR_PUBLISH` 传回发布页。这样「跑完变体再跑普通相似品」不会因为 `variantPending` 残留而误填标题。
- **不换图就失败**：`applyVariant` 读不到数据、标题写不进去、素材搜不到、第一张图没变化，都直接判该条失败，
  绝不"发一个没改标题/没换图的商品"。
- **失败标签页不留**：变体一次开十几二十个发布页，失败页由后台一并关闭（原因已随结果回传）；
  普通相似品失败仍保留页面，方便人工看校验提示。
- **半自动兜底仍保留**（第六节）：如果平台改版导致自动换图失效，错误信息会写明卡在哪一步
  （没找到「图库替换」/ 素材库没搜到 / 第一张没更新），此时退回「人工换图 + 继续」只需要改发布页那一段，
  外层队列不用动。

## 十二、2.1.1：两个标题 + 只填不发（本次改动）

### 1. 命名

侧边栏里的展示名调整，内部 `featureId` 与 storage 键保持不变（避免历史任务记录和已存数据失联）：

| 原展示名 | 现展示名 | featureId |
|---|---|---|
| 批量发布相似品 | **旧链上新** | `douyin.similar-publish` |
| 批量复制变体 | **裂变链接** | `douyin.copy-variants` |

### 2. 商品标题 + 导购短标题

发布页上其实有两个标题框，之前只填了第一个：

- **商品标题**：整条标题，上限 60（截图里 58/60）；
- **导购短标题**：24 字上限，标题里含英文或数字时只能填 23 个（平台按显示宽度算）。

填写规则（`app/shared/titles.js` 与 `similar.js` 各一份，测试比对一致性）：

1. 按 `Array.from` 切字符，避免把 emoji 的代理对切一半；
2. 标题含 `[0-9A-Za-z]`（含全角）→ 取前 **23** 个，否则取前 **24** 个；
3. 截断后若末尾是空格/逗号/顿号之类，去掉（不影响字数上限）；
4. 不足 24 字原样写入。

两个框的识别顺序（`titleFields()`）：

1. `placeholder / aria-label / name` 里写了「导购短标题」「商品标题」；
2. 输入框往上 5 层内，**最近一层含「标题」字样且长度 ≤ 120** 的容器文字；
3. `maxlength` 兜底：> 24 的当商品标题，≤ 40 的当短标题。

第 2 条额外带 `exclude`：外层容器同时含「商品标题」和「导购短标题」时直接放弃这一层，
交给第 3 条按长度区分——否则商品标题框会被认成短标题框，把 24 字短标题盖到 60 字框上。
写入前还有一道硬保险：两个引用相同就跳过短标题，宁可不填也不覆盖。

短标题写不进去或被平台截短：

- 被平台截短（实际值是目标值前缀）→ 记日志、按实际值继续（`lenient`）；
- 完全写不进去 → 判该条失败；
- 页面没有这个框 → 跳过，不阻断（平台改版去掉了字段也能照常跑）。

### 3. 只填不发

`views/feature-copy-variants.js` 顶部一个开关：

```js
const PUBLISH_ENABLED = false; // 验证稳了改成 true，复用已有 publishNow()
```

- 列表页把 `publish` 写进 `variantPending`，发布页 `applyVariant()` 返回后判断 `pending.publish === false`；
- 只填模式：填完两个标题与主图就回报 `SIMILAR_PUBLISH_DONE{ok, filled, keepTab}`，**不点「发布商品」、不关标签页**；
- 后台 `SIMILAR_PUBLISH_DONE` 见到 `keepTab` 就不关页，把 `filled` 一起转回列表页；
- 列表页结果项带 `filled: true`，复制文本的状态列写「已填未发」，与「成功」区分；
- 面板第 3 步把「本次动作」写清楚，第 4 步提示页面会保留、核对后手动关闭。

## 十四、2.1.3：确认弹窗必须选中「发布相似品」

### 现象

点「发布相似品」后弹出的「请确认要进行的操作」弹窗有两个卡片：**发布相似品** / **设置渠道品**。
平台把它默认停在 **设置渠道品** 上（弹窗顶部还在推「如需创建自播/达播商品,请优先设置渠道品」），
旧代码只做了一次 `pickCard()` + 一下点击，既不校验也不重试，结果带着渠道品点了「确定」。

### 旧实现为什么失效

- `pickCard()` 取的是「文本以『发布相似品』开头且最内层」的节点 —— 那是**标题文字那一层**，
  不是整张卡片；
- `mouseClick` 默认走 `elementFromPoint`，而弹窗还在入场动画里，坐标随时在变，
  点到卡片之间的空隙或下一张卡片都可能；
- 最关键：**点完没有任何校验**，选没选中都继续点「确定」。

### 新实现

`findOptionCard(dialog, title)`：

- 标题层 = 文本几乎只有该标题的最内层节点；
- 卡片壳 = 从标题往上第一个把描述也包进来的祖先（不能取「最内层含描述」，那会落到描述文字上，读不到边框）。

`cardChecked(card)` 依次判断：

1. 内部单/复选框是否勾上；
2. `aria-checked / aria-selected`；
3. 蓝色描边 / 蓝色阴影 / 蓝色轮廓（`b ≥ 150 且 b-r ≥ 40、b-g ≥ 20`）；
4. 极浅蓝底色（`b ≥ 200 且 b-r ≥ 8、b-g ≥ 4`，白底与灰底都不满足）；
5. 右上角 8~26px 的勾选角标。

`chooseSimilarOption(dialog)`：

- 弹窗里没有「设置渠道品」→ 说明不是二选一，**不动**（保持旧链上新原来能跑的行为）；
- 「发布相似品」已选中、且「设置渠道品」未选中 → **一次都不点**；
- 否则依次点「卡片壳 → 标题 → 卡片壳」，每次点前等弹窗尺寸稳定（`waitStable`），点后校验；
- 第二重判据：两张卡片的样式签名（class + 边框 + 阴影 + 底色）**互换**，兜住我们认不出的选中样式；
- 三次都不成 → **点「取消」并抛错**，日志里带上两张卡片的 `class`、边框颜色 —— 绝不带着渠道品继续。

自检（`SIMILAR_DIAG`）在弹窗存在时会输出两张卡片各自的「已选中 / 未选中」与边框、底色、class。

版本 2.1.3 / 页面脚本 0.9.5；`tests/check-dialog.js` 新增 15 项二选一仿真（默认停渠道品 / 点不动必须报错 / 已选中不瞎点 / 单选项不动）。

## 十五、2.1.4：短标题按字符位算；素材库必须真正选中

### 1. 导购短标题：24 个**字符位**，不是 24 个字

实测日志：一条 28 字标题被截成 24 个汉字写进短标题框，平台判超限。
抖店的 24 上限按**字符位**算：中文/全角/emoji 各占 2 位，英文、数字、半角符号占 1 位。
所以 24 个汉字等于 48 位，远超上限；纯中文最多只能填 **12 个字**。

新规则（`app/shared/titles.js` 与 `similar.js` 各一份，测试比对一致性）：

```js
一个字符的宽度：0x20~0x7E 的 ASCII → 1，其余 → 2
逐字累加，超过 24（含英文/数字时 23）就停
末尾的分隔标点去掉（不影响字符位）
```

- 纯中文 → 12 个字；
- 含英文/数字 → 最多 23 位（例如「除湿袋A」×3 + 「除」，10 个字 = 23 位）；
- 侧边栏配对预览的短标题列，鼠标悬停会显示「N 字符位，上限 24」。

### 2. 素材库：搜到了 ≠ 选中了

实测日志出现了「已点确定」，但截图里素材卡片没有勾选，弹窗一直开着 —— 旧代码的问题是：

- `selectLibraryCard` 点一下卡片中心（那里是图片，勾选框在**右上角**）；
- 补点 `input[type=checkbox]` 时走的是坐标命中，而那个 input 常被透明样式或外层容器盖住，点不到；
- **返回值是 `null`（无法判定）时照样继续点「确定」**；
- 点完确定只 `await waitFor(弹窗关闭)`，没检查结果，白白等 10 秒再报一个含糊的错。

新实现：

`selectLibraryCard` 依次尝试并**每一步都校验**：

1. `box.click()`（原生点击，最可靠，直接触发 change）；
2. 对勾选框直接派发事件（`strict`，不走坐标命中）；
3. 勾选框外层容器（`strict` 与坐标各一次）；
4. 缩略图右上角（`ratio [0.9, 0.1]`，勾选框压在那）；
5. 卡片中心。

校验用 `cardSelectedState`：原生 checkbox → `aria-checked` → 自定义勾选类名；
认不出勾选控件时，退一步看卡片外观（class / 边框 / 阴影 / 底色）**是否变化**。

选中失败 → 关掉弹窗、抛错，**绝不点「确定」**（否则可能把主图换成别的图）。

点「确定」之后新增两道校验：

- 6 秒内弹窗必须关闭，没关就补点一次，仍不关 → 报「平台没接受，多半是素材没真正选中」；
- 弹窗关闭后再等主图 `src` 变化，没变 → 报错。

版本 2.1.4 / 页面脚本 0.9.6；`tests/check-variants.js` 新增 16 项（字符位 12 项 + 素材选中 4 项）。

## 十六、2.1.5：勾选框在右上角，按它的真实位置点

2.1.4 按「右下角」去点，截图证实勾选框是压在**缩略图右上角**的小方块，所以那一路必然点空。
这一版不再猜方位：

1. **先问元素**：卡片里有 `input[type=checkbox]` / `[role=checkbox]` 时，读它的
   `getBoundingClientRect()`，换算成卡片的相对坐标（`boxRatio`）再点 —— 位置由平台自己给，不靠猜；
   元素尺寸为 0（被藏起来）才跳过这一步。
2. **再按方位兜底**：缩略图右上角 `[0.9, 0.1]` → 卡片右上角 `[0.9, 0.1]` → 卡片中心。
   右上角排在中心之前；右下角那一路已删除（截图证明它不存在）。
3. **判据拆开**：
   - `cardSelectedState` 只认 `input.checked` 与 `aria-checked`；
   - 自定义勾选方块这类认不出的，用 `checkMarks`（卡片内带 `checked/selected` 类的元素个数）

   早先版本把「卡片里有 checked 类」直接当「已选中」，一旦平台给未选中的卡片也挂了常驻类，
   就会把所有卡片判成已选中、带着没选中的素材去点确定 —— 比选不中更危险，所以改成比较差值。

4. 点「确定」后仍校验弹窗是否真的关闭，再校验主图 `src` 变化。

## 十七、2.1.6：素材库「有时搜不到」的三个根因

用户实测：同一条流程反复跑，**有时能搜到、有时搜不到，而且每次搜不到的那张图都不一样**。
真人手动搜同一个名字一定能搜到，说明图存在、名字也没错，问题在脚本侧的时序与定位。

### 根因 1：搜索框的值被平台打回去（主因）

素材库搜索框是 React 受控组件。旧代码用 `setNativeValue` 直接改 DOM 的 `value`，
再立刻按回车：

```js
setNativeValue(input, imageName);
pressKey(input, 'Enter', 13);
```

`setNativeValue` 只改 DOM 值、不更新组件的 state。回车触发平台按 **state 里的旧关键词**
（上一次搜的那张图，或空串）去搜；随后 React 重渲染，把输入框的值也打回旧词。
于是平台显示的是**上一张图的结果**，我们却在等这一张 —— 取决于「重渲染」和「回车」谁先到，
所以时好时坏，坏的那张每次不同。

新实现 `typeLibrarySearch()`：

1. `focus()` + `select()`，先 `setNativeValue(input, '')` 清空（残留关键词会干扰）；
2. 用 `document.execCommand('insertText', false, name)` 写入 —— 它触发真实的
   `beforeinput` / `input`，React 会同步 state；
3. 等 320ms，**回读 `input.value`**，被打回就再插一次；
4. 值站住了才按回车；返回值告诉调用方「值有没有留住」，留不住会写进日志。

### 根因 2：只认第一张卡片

旧代码 `findFirstMatch` 只看 `list[0]`：一旦搜索没生效（列表是整个文件夹）或者平台返回多条，
目标不在第一张就直接判「没搜到」。改成遍历**全部卡片**并按匹配分取最优：

```js
nameScore(cardText, imageName)  // 3 = 文件名全等，2 = 去扩展名相等，0 = 不匹配
```

文件名先标准化再比：小写、去空白、全角 `（）` 转半角 `()`、全角 `：` 转 `:` ——
平台把「创意图 (2).jpg」显示成「创意图（2）.jpg」也能认出。仍然不用「包含」，
避免 `1.jpg` 命中 `11.jpg`。

### 根因 3：弹窗节点会整块换掉

搜索后素材库常常整块重渲染，之前抓到的 `dialog` 元素脱离文档，
`libraryCards(dialog)` 就在一个死节点里找卡片 —— 结果永远是空。
所有查询改为 `liveDialog()`：节点 `isConnected` 为 false 时重新 `findLibraryDialog()`。
同理，`selectLibraryCard` 现在接受**取卡片的函数**，每换一种点法都重新取一次，
不会对着已经消失的元素点击。

### 兜底顺序

```
输入（execCommand，回读校验）
 → 等 8s 看目标是否出现
 → 补点「查询 / 搜索」按钮（没文字时找输入框右侧的图标按钮）
 → 清空重输一次 + 再点「查询」
 → 列表向下滚动 8 屏（搜索彻底没生效时，整文件夹里找）
 → 都没有才报错，并把「列表共几张、前三个叫什么」写进错误文案
```

每一轮失败都会写日志，例如：

```
素材库已打开，搜索「创意图 (2).jpg」
回车后没匹配到（列表 16 张：创意图 (1).jpg、创意图 (2).jpg、创意图 (3).jpg），补点「查询」再等
```

有了「列表 N 张 + 前三个名字」，下次再出问题能直接看出是「搜索没生效」还是「名字对不上」。

版本 2.1.6 / 页面脚本 0.9.8；`tests/check-variants.js` 新增 24 项
（文件名标准化 6 项 + 搜索链路结构 10 项 + 搜索框写入 7 项 + 选中重新取卡片）。

## 十八、2.1.7：搜到了却判「没搜到」——取文件名把名字切断了

用户实测日志（16:18:45 起）：

```
素材库已打开，搜索「创意图 (4).jpg」
回车后没匹配到（列表 1 张：(4).jpg），补点「查询」再等
还是没匹配到，清空搜索框重新输入一次
搜索可能没生效，改为在列表里往下滚动寻找
```

**「列表 1 张：(4).jpg」就是目标图。** 搜索其实一次就命中了，是我们自己把名字读错、
再自己把搜索框清空、最后判成失败 —— 用户看到的「等了一会又把搜索清空了」就是这段重试。

### 根因：`cardName` 按空白切文件名

```js
const found = text.match(/[^\s/\\]+\.(?:jpe?g|png|webp|gif|bmp)/i);  // 旧
```

`[^\s/\\]+` 把空白排除在字符类外，遇到「创意图 (4).jpg」里的空格就**从空格后开始匹配**，
于是拿到 `(4).jpg`。而 `nameScore` 要求全名相等或去扩展名相等，两者都对不上 → 判 0 分
→ 触发「清空重输」。文件名带空格（`创意图 (4).jpg`、`产品图 B-01.jpg`）必然踩到，
所以是「每次搜不到的都不一样」的另一个来源。

### 修法

1. `pickFileName()`：改成「取到扩展名结尾为止」——
   `text.match(/^(.*?\.(?:jpe?g|png|webp|gif|bmp))/i)`，名字里的空格原样保留；
   名字后面的尺寸（`1080*1440`）因为落在扩展名之后，自然被截掉。
   **不**做「去掉 `800*800` 这种尺寸前缀」的清洗：素材名本身就可能叫 `800*8001.jpg`。
2. `cardName()` 多口径取名字：文件名节点的文本 → 节点 `title` → 图片 `alt`/`title`
   → 卡片 `title` → 整张卡片文本，取其中**最长**的那份。
   平台把名字拆成两个节点时，前半截丢了、`title` 里有全名，这样也能拿全。
3. `nameScore()` 增加一档「尾段编号」：只读到 `(4).jpg` 这半截时，
   若目标名按空格切的最后一段也是 `(4).jpg`，给 1 分（低于全名的 3 分）。
   只对 `(数字).jpg` / `数字.jpg` 这种纯编号尾段生效，`1.jpg` 与 `11.jpg` 仍不会互相命中。
4. 重试链改成「不毁掉已生效的搜索」：

```
输入（execCommand，回读校验）
 → 等 8s
 → 补点「查询 / 搜索」
 → 只剩 1 张、且搜索框里还是我们的词 → 直接认定这张（名字没读全的兜底）
 → 仅当搜索框的值被平台改掉时，才清空重输
 → 列表向下滚动
 → 都没有才报错，并把卡片原文一起写进错误文案
```

### 同时修的第二个问题：扩展自己开的发布页没被接管

16:20:25 扩展代开的创建页，到 16:20:51 报「35 秒内无新标签页」。
只靠 `chrome.tabs.onUpdated` 的 `complete` 事件会漏（标签在事件派发过来之前就已加载完），
于是页面开着、列表页却空等到超时。改为：

- `chrome.tabs.create` 之后**主动轮询** `chrome.tabs.get`（800ms，最多 60s），
  一 `complete` 就 `handleReleaseTab`；
- 把标签最终停在哪个 URL 写进日志：非抖店页 / 回到 `/list` / 60s 未加载完，三种原因分开报；
- 等待时长 25s → 45s；
- 超时撤销登记后，那条创建页若之后才加载完，直接关掉（`similarOrphans`，3 分钟有效），
  避免每条失败都留一个残页。

## 二十、2.1.9：点发布撞上「商品类目识别中，请完成后再发布」

用户实测（截图）：操作稍快时，点「发布商品」弹一句

> ⓧ 商品类目识别中，请完成后再发布

平台自己还没把类目认完，这一下点击不会被受理；等几秒再点就正常了。
以前脚本把这一下当成「失败」，整条记录白跑（或者干等到 3 分钟超时）。

### 为什么要单独分出一类提示

发布页的失败判定一直是「点击后新冒出来的校验文案 → 立刻判失败」，靠 `ISSUE_PATTERN`
过滤。类目识别中**不是校验失败**，它是平台还没准备好；把它和真失败混在一起，
就会出现「明明只差 3 秒」的记录被标红。

新增 `isBusyNote(text)` 把两拨文案分开：

| 归为「等一会儿」（重试） | 归为「真失败」（报错退出） |
|---|---|
| 类目识别中 / 识别类目中 / 类目校验中 | 商品标题不能为空、请选择类目 |
| 加载中、处理中、校验中、检测中、审核中 | 发布失败：xxx |
| 请稍候、请稍等、请等待、请完成后再、稍后再试 | 网络异常，请稍后再试 |

最后一行是关键：`网络异常，请稍后再试` 同时命中两边，所以 `isBusyNote` 先看有没有
`失败/错误/异常/不能为空/请填写/请选择/请完善/必填/未通过`，有就一律按失败报，
不让重试把真问题掩盖成「一直在提示」。

### 改法

1. **点之前先等**：`waitCategoryReady()` 在第一次点击前，若页面上有类目识别中的浮层，
   等它消失（最多 30s）。只认浮层不认整页文本 —— 类目字段旁边常驻的「识别中」
   不是浮层，认了会白等。
2. **点之后能重试**：`publishNow()` 改成 `for attempt = 1..4`：
   - 每次点击前**重新找**「发布商品」按钮（类目识别结束后按钮常被重建，抱旧节点会点空）；
   - 每次点击前重新取 `baseline`（上一次的浮层不能算到这一次头上）；
   - 等到「商品提交成功」→ 结束；等到真失败文案 → 立刻退出，不浪费重试；
   - 等到类目识别中 → 等提示消失（最多 25s）→ 再点一次，日志写「第 N 次点击」；
   - 既没成功也没抓到提示（点击没被接住）→ 还有预算就再点一次。
3. **预算**：整体 3 分钟，单次等待夹在 20~60s 之间；4 次都没过，错误文案直接带平台原话
   （「平台一直在提示「商品类目识别中，请完成后再发布」，已重试 4 次」），
   一眼能看出是平台没就绪还是我们点坏了。
4. 重试判定用 `findBusyNote()`：先找浮层，找不到再按整页完整短语兜底
   （`类目识别中` / `请完成后再发布`），避免浮层 class 名不带 toast 时漏掉。
